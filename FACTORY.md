## Reproduce the factory

1. Configure three distinct coding seats in one Band room with the generic mandates. Put the actual harness/model on the first lines of each mandate. Keep product requirements in the room dispatch rather than standing instructions.
2. Supply explicit absolute locations for read-only requirements, a separate result repository and per-stage evidence. Prepare Git, Docker and the challenge harness before dispatch. Keep credentials outside the result and do not request new paid services during execution.
3. Dispatch the complete task once. A sequence may be dispatched together, but stages advance in order after independent acceptance. Planner reads the guide and complete specifications, records the pinned input revision, publishes a durable acceptance plan and assigns implementation and verification through literal seat handles.
4. Every handoff carries the entire applicable task, guide requirements and inherited/current specifications, including deployment limits. A file path alone is insufficient. Builder creates the complete stage folder, tests it, commits and freezes a full revision.
5. Reviewer checks that exact clean revision with specification-derived cases, actual cumulative isolated harness runs, realistic populated upgrades and browser behavior where applicable. Save commands, source snapshots/hashes, constrained-container configuration, counts, timings and rendered screenshots in new run directories.
6. Return genuine defects with expected/actual behavior and a reproduction. Builder repairs in a new commit; Reviewer rechecks. Preserve original failures and distinguish a bad assertion, transport problem or synchronization mistake from a service defect. Correct work may be accepted on the first candidate.
7. After acceptance, copy the entire folder forward and extend only the copy. Earlier trees remain immutable and build alone; no shared runtime imports, symlinks or submodules. Preserve the actual collaboration history without amend, rebase or squash.
8. Complete a four-folder isolated package check and a separate root-documentation audit. Report precise local readiness and unresolved limitations. Room export, presentation/video, publication and event submission remain explicit operator activities, outside this authorized run.

Private tasks track personal execution; shared cards coordinate cross-seat ownership. The active room plan is an immutable Markdown snapshot. Message timeouts are recorded as unanswered waits, not as acceptance or proof that a participant is unavailable. Existing assignments are not automatically resent. Agents resolve the authorized stage work without asking the human for steering.

## Implementation and tradeoffs

The service uses Python's standard library, bundled timezone data and in-memory state under one process lock. One image contains the runtime and all browser assets. The single-container contract allows ephemeral state, so this chooses simple, inspectable transactions over restart persistence or horizontal scaling. HTTP is the public interface; no judge-host Python imports are required.

State-changing operations prepare detached state and response data before publication. Independent Stage 1 review found that a lock alone did not prevent a rejected operation from leaving a mutation behind. Iterative JSON processing also preserves deeply nested ignored fields in complete retry bodies. The extra copying work is measured under the required concurrency and request bounds.

Later folders extend the model rather than rewriting earlier history: canonical approved table pairs, original idempotent receipts, immutable policy snapshots, versioned histories, recurring agreements and their permanent diner exceptions. Runtime assets are local. The English browser flow emphasizes restaurant and seating labels, clear reservation outcomes and usable 375px layouts. Additional administrative screens are not required by the later specifications.
